## Engine — built and proven this pass

1. **Deterministic renderer (`render.py`).** Regenerates `current/*.xlsx` from `account.json`/`brand_profile.json`/`actions.json` against a fresh copy of `_standard/Standard_Blue_Sheet.xlsx` every time (a pure function of the dossier, not an incremental edit), archiving whatever was in `current/` into `history/` first. Run against Pollo Campero and spot-checked cell-by-cell against the original source workbook — matches. Known limit: row counts are capped at the current template's row allowance per tab (10 buying influences, 4 strengths, 5 red flags, 13 tech-stack rows, 14 actions, 7 commercial-model rows); an account exceeding that raises rather than silently truncating, since row-insertion isn't built yet.
2. **Validator (`validate.py`).** Checks, directly against the JSON (Section 15, adapted): no `status: confirmed` field without evidence; every `evidence_id` referenced actually resolves in `evidence.jsonl`; governance-gated fields (Section 8) are never `confirmed` by automation; contradictions referenced from `brand_profile.json` exist in `contradictions.json`; actions carry only supported RBB mutation types (Section 13); stale (>90 day) `as_of` dates are flagged; required workbook tabs are present; no literal Excel error tokens or lowercased (LibreOffice-unparseable) formulas got baked into a save. Smoke-tested that the evidence-reference check actually fires on a bad ID, not just a vacuous pass. **Cannot recalculate formulas** — no LibreOffice in this environment, and the xlsx skill's own `recalc.py` fails outright on this machine's Python 3.9 (`tempfile.TemporaryDirectory(ignore_cleanup_errors=...)` needs 3.10+). Formula cells were hand-verified as syntactically intact and correctly referenced, which is not the same as a verified recalculation.
3. **Impact-review engine (`impact_review.py`).** Implements the safe-apply/approval-queue split Todd specified: takes a list of proposed field-level changes plus one evidence record, refuses to touch an unactivated account, classifies each change (governance-gated fields per Section 8 → `review_queue.json` as a proposal, never applied; everything else → applied directly to the dossier), re-renders and re-validates if anything was auto-applied, and writes a `change_log.jsonl` entry. **Ran end to end** against a synthetic two-part test event for Pollo Campero (Diego Haro's title change — safe, auto-applied; a fabricated claim that Diego says Jorge has EBI authority — correctly refused and queued instead, since role/EBI attribution is governance-gated regardless of who reports it). The synthetic event, its evidence record, the queued item, and the one history archive it produced were all reverted afterward so the live dossier reflects only real data — the proof is in this gap report and the session transcript, not left sitting in Pollo Campero's record.

## Still not built (blocks calling this "automated")

1. **Wiring into the live canonical registry.** `impact_review.py` is a standalone library — nothing in `system/scripts/mutations.py`, `ri_events.py`, `ecosystem_intelligence.py`, or `eolms.py` calls it yet. This is the actual remaining gap between "the mechanism works" and "the pipeline runs itself." **A survey of these four scripts' write paths was completed 2026-08-21** (post-park; filed here for next sprint, not acted on) — key findings for whoever picks this up:
   - **No file uses a field literally called `account_id`.** The closest equivalents per file: `mutations.py` has a person `id` (contact) and free-text `--company`/`--companies` strings, plus a strategic-operator `id` with `--companies-owned`/`--brand` lists — no single normalized company id. `ri_events.py` events carry `entities.companies[].matched_id`, which *is* effectively an account id, but it's inside the free-form `event` dict, not a named parameter of `append()`. `ecosystem_intelligence.py` has the strongest match: `entity_id` / `from_entity_id`/`to_entity_id` on nearly every mutating function (`promote_posture`, `promote_confidence`, `watch_list_cmd`, `merge_brand_entities`). `eolms.py` only has a free-text `--orgs` list, no single id.
   - **Best hook points (lowest shared choke point per file, so a hook fires regardless of entry point — CLI, subprocess, or in-process import):** `mutations.py`'s individual `cmd_*` functions each have their own single write call (no one shared writer across all of them); `ri_events.append()` (single shared writer, all 4 production callers funnel through it); `ecosystem_intelligence._write_graph()` (single shared writer); `eolms._save()` (single shared writer, called by every mutating `cmd_*`).
   - **The codebase's own established pattern for this exact kind of hook** (found in two places, both worth copying): (a) `mutations.cmd_loop_close` → `eolms.close_by_ledger_id()`, wrapped in try/except commented "EOLMS sync is additive, never blocks the ledger close"; (b) `ecosystem_intelligence.py`'s `audit_log.append_event()` calls, safe to call unconditionally because `audit_log.append_event` is documented to never raise. Any Blue Sheet hook should follow one of these two patterns — call it *after* the primary write/validation already succeeded, never before, and never let it block or roll back the canonical write.
   - **Production wiring** (where a hook would actually take effect vs. being dead code): `ri_events.append()`'s real unattended caller is the 04:00 LaunchAgent chain (`morning_pipeline.py --scan-only` → `refresh_all.py` → `passive_ri_ingest.py --cache`). `ecosystem_intelligence.py` mutations reach production both as API-server subprocess calls (`updateWatchList`, `postPromoteClaim`) and in-process imports from several other scripts. `eolms.match_and_transition()` fires with **no confirmation gate** from the executive-declaration API route — the highest-risk existing entry point, explicitly documented as such ("CEO declarations are the highest-fidelity source"). `mutations.py`'s `cmd_*` functions are called in-process by ~8 other scripts constructing fake argparse namespaces, plus via the API server behind `confirm=true`.
   - **Fragility warnings worth respecting:** `ecosystem_intelligence._write_graph()` writes to disk *before* running schema validation and does not roll back on validation failure (unlike `mutations.py`'s baseline-index path, which does snapshot-and-rollback). `eolms.py`'s `match_and_transition` scoring thresholds are tuned constants with an explicit "a wrong auto-close is worse than no auto-close" design rationale — do not touch without understanding it. Several named prior defects (`RB-2026-07-15`, `RB-DEFECT-040/9.70`, `TOUCHCONTACT-PROJECTION-SYNC-001`) exist specifically because two canonical stores drifted out of sync after an incomplete write path — exactly the failure mode a careless Blue Sheet hook could reintroduce.
   - Full investigation transcript is not preserved beyond this summary; re-run a similar survey if finer detail is needed before implementing.
2. **Claim extraction from real events.** The dry-run's `ProposedChange` list was hand-built to exercise the safe/gated split. Turning a real email, meeting note, or registry mutation into that same structured list (identity resolution, dedup, classification — spec Section 10 steps 2-6) is not implemented.
3. **Row-insertion in the renderer.** An account whose buying-influence/tech-stack/action count exceeds the template's current row allowance will raise, not adapt. Fine for Pollo Campero today; will need handling before a materially different account gets activated.
4. **Presentation View 1 & 2 drift risk.** These two tabs are regenerated as static literals by `render.py` (matching the reference file's own behavior, which uses no formulas here) — accurate immediately after every render call, but only until the underlying script that calls `render()` is itself reliably triggered by item 1 above.
5. **Portfolio health workbook.** `_portfolio/portfolio_health.xlsx` is referenced in the folder contract and registry but was not built — this is explicitly Phase 2 scope.

## Architectural question — RESOLVED 2026-08-21

`system/CANONICAL_REGISTRY.yaml` listed two unresolved governance decisions — "establish the canonical account registry" and "establish the canonical opportunity registry" — that `blue_sheets/accounts/*/account.json` overlapped with. Todd resolved the relationship (not those two underlying items themselves, which remain open):

- The Blue Sheet is **downstream** of the canonical registry, created only for a targeted account with a specific sales motion, and only on Todd's explicit direction — never auto-created from the Section 16 active-portfolio policy alone.
- Once a Blue Sheet exists for an account, the canonical registry becomes a **major, ongoing source of updates to it**.
- The repeatable pipeline: a canonical-registry mutation checks whether the touched account has a Blue Sheet; if so, it mutates the Blue Sheet (impact review → auto-apply safe / queue judgment-sensitive); if not, nothing happens.

This is now encoded in `system/CANONICAL_REGISTRY.yaml`'s `blue_sheets` domain (`architectural_decision`, `field_provenance_split`, `activation_policy`, `mutation_owner`) and in `blue_sheet_registry.json` (`activation_authorized_by`/`activation_date` on every account). Practical consequence for account.json/brand_profile.json going forward: split every field into **registry-sourced** (identity, footprint, tech stack, actions/loops, public facts — synced from upstream, never hand-edited only here) versus **blue_sheet-native** (qualification scorecard, buying-influence role/mode/personal-win/preference/rating, euphoria-panic, best action plan — Miller Heiman judgments that only exist in the Blue Sheet layer and are never written back upstream as canonical fact).
