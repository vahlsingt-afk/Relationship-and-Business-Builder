`intelligence_action_queue.py` ran as its own `morning_pipeline.py` scan step (right after `sales_opportunity_radar`), before `competitor_intelligence_review_scan` (a later scan step) and before `intelligence_ramifications` was ever computed (only ever computed inside `daily_brief.py`'s report construction, never persisted by its own pipeline step). ### Bonus: acceptance-gate severity bug found by the full test suite

Running the full `system/tests/` suite (not just a focused subset) after items 1–3 surfaced 2 pre-existing failures in `test_brief_quality_checks.py`, unrelated to anything above. `check_no_cross_day_repeat_without_grace()` in `brief_acceptance_check.py` hardcoded severity `"fail"` while its own docstring said "WARN-only since some repeats (multi-day corporate grace) are intentional" and `check_brief()`'s own contract says "`passed` reflects only FAIL-severity findings." Net effect: any legitimate cross-day repeated URL — the exact case this check exists to tolerate — incorrectly blocked the whole brief's acceptance gate instead of just flagging for review. One-line fix (`"fail"` → `"warn"`).

That fix then surfaced a THIRD, directly conflicting test: `test_brief_acceptance_gate.py::test_cross_day_exact_article_repeat_is_release_blocking` asserted the opposite (`severity == "fail"`) for the same function. Investigated on the merits rather than picking a side by guessing: `render_intelligence_brief.py` has a real, deliberate multi-day "corporate grace" re-render mechanism (`_is_duplicate`/`_story_ledger.should_render`, up to `CORPORATE_DEDUP_GRACE_DAYS`) that legitimately re-renders the same URL across multiple days for corporate-badged stories (acquisitions, etc.) — this is expected, correct behavior, not a dedup failure. A backstop check that can't see the per-section grace period blocking on every such re-render would create frequent false gate failures for entirely healthy sends. That confirms WARN is the correct, intended design; the acceptance-gate test was the stale one. Fixed that test's assertion and renamed it (`..._is_flagged_but_not_release_blocking`), keeping its useful URL-normalization scenario (same article, different tracking-param URL, still detected as a repeat) intact.

This is the same bug *class* Codex's own handoff already fixed once today (the "near 52-week low" story-cluster false positive) — a release-gate check being stricter than its own design intent. Worth remembering for whoever continues this cycle: **run the full suite, not just a focused subset, before writing "N passed" into a handoff** — Codex's own 34-test receipt didn't include this file, so this sat live and undetected, and the fix itself needed cross-checking against a *second* test with a directly opposing assertion before it could be trusted.

### 5. Calibrate over outcomes — prerequisite built, tested, and live; outcome-correlation itself still open

The real gap found while scoping this: `intelligence_action_queue.build()` fully **regenerates** `intelligence_action_queue.json` from scratch every cycle (unlike `competitor_intelligence_review.py`'s `review_queue.json`, which dedupes against its own prior state and preserves it). There was no way to mark a queue item accepted/rejected/deferred that would survive the next `build()` call — any status stamped on an item was silently wiped the next morning. Calibration needs a durable decision record to calibrate against, so this had to come first.

Built:
- `STATE_PATH` (`system/.cache/intelligence_action_queue_state.json`) — a durable side-store, merged back into every fresh `build()`, mirroring `sales_opportunity_radar.py`'s own state-merge pattern (`sales_opportunity_radar_state.json`) rather than `review_queue.json`'s append-only model, which doesn't fit a fully-rebuilt-every-cycle view.
- `intelligence_action_queue.resolve(queue_id, disposition, *, note="")` — `disposition ∈ {"accepted", "rejected", "deferred"}`. Snapshots `item_type`/`entity`/`action_class_at_resolution`/`priority_score_at_resolution` at resolution time (the live item re-scores or can disappear on the next cycle, so without the snapshot a later calibration pass couldn't tell what was actually being judged). Writes via `cic.save_json_atomic` (same corruption-safe write `competitor_registry.json` uses after RB-DEFECT-071).
- `build()` now merges resolutions back onto every fresh row (`status`, `disposition`, `disposition_note`, `resolved_at`) and reports `resolution_counts: {pending_review, resolved}` alongside the existing `action_class_counts`. A resolution on an item that later stops regenerating (its underlying signal cleared) still survives in `STATE_PATH` — proven by test, not just asserted.
- `POST /intelligence-action-queue/{queue_id}/resolve` (`operation_id=resolveIntelligenceActionQueueItem`) in `server.py` — same shape as `resolveCompetitorReviewItem`: doesn't itself contact an account, create an opportunity, or change a pursuit stage, purely records the disposition.
- `GET /intelligence-action-queue` gained an optional `status` filter (`pending_review`/`resolved`) alongside the existing `action_class` filter.
- `daily_brief.py`'s `_intelligence_action_queue_items()` now filters to `status == "pending_review"` before slicing the top 8 — without this, a resolved item would keep occupying a top-8 slot forever purely on `priority_score`, crowding out items Todd hasn't seen yet. Resolved items stay fully visible via `getIntelligenceActionQueue` for audit/calibration, just stop being re-surfaced daily.

## Beyond the handoff: hardening RB's actual "connect the dots" engine

Todd's framing question: what else strengthens intelligence gathering so the CoS connects dots and makes better recommendations. Investigated the real engine (`entity_convergence_scan.py`, which delegates the actual cross-store correlation to `signal_synthesis.py`) rather than speculating, and found two real, live, concrete gaps in its core entity-matching primitive, `signal_synthesis._entity_matches()`.

### 1. A live over-matching (false-positive) bug, confirmed before touching anything

`_entity_matches()` did a raw substring check for the full entity name, then excluded any token under 4 chars from its multi-token AND-fallback entirely. Confirmed live, before any fix: `_entity_matches("Qu", "Same-store sales grew this quarter after the acquisition closed.")` → `True`. **"Qu" is a real, actively-tracked competitor** — this means any text anywhere in `market_signals`, `active_threads`, `ri_events`, `passive_ri`, or `social_overlay` containing "quarter", "acquisition", "equity", "require", or "unique" (any text with consecutive q-u letters) was false-positiving into Qu's convergence signals every single day this ran. `_entity_matches("PAR", "...comparable...")` also matched — the exact collision class already fixed once in `intelligence_triage.py`'s registered-artifact matcher (RB-DEFECT item 2 in Codex's own handoff table), but never here, in a completely different module.

Fixed: every entity-name token is now matched word-boundary-safe when <= 4 chars (token-set membership, same `_SHORT_TOKEN_THRESHOLD` discipline as `intelligence_triage._term_in_text()`) and substring-safe when longer, with ALL tokens required (stricter than before, since short tokens are no longer silently dropped from the requirement). Verified: 71 existing tests still pass unmodified (the fix is a strict refinement, not a behavior change for anything already covered), plus 4 new regression tests built directly from the live Qu/PAR/NCR examples above. Re-ran `entity_convergence_scan.py` against real production data afterward: 290 entities, 0 errors.

### 2. A live under-matching (missed-connection) gap — the actual "connect the dots" weakness

Separately: a signal mentioning a tracked entity only by an alternate name (e.g. "NCR" for the competitor whose canonical name is "NCR Voyix") never counted toward that entity's convergence pattern at all — `_entity_matches("NCR Voyix", "NCR announced...")` → `False`, correctly, but nothing upstream ever tried the alias "NCR" either. This directly connects to a real, already-known, previously-unresolved issue (a `vendor-ncr`/`vendor-ncr-voyix` duplicate-entity ambiguity flagged in an earlier session). `entity_convergence_scan.py` — RB's actual "connect the dots" engine — was silently under-counting convergence for any company with a rebrand, an abbreviation, or an acquisition-driven name change, with no error or visible symptom; it just connects fewer dots than reality has.

Fixed, without touching the underlying duplicate-entity-record problem at all (that's a separate, riskier data-model question, not decided here): `signal_synthesis.synthesize_entity_signals()` gained an optional `aliases` parameter — when passed, it collects signals under the primary name AND every alias from all six stores, merges and dedupes by `signal_id` BEFORE pattern-scoring runs once over the combined evidence (never scores per-alias and combines after, which would double-count a signal found under two names as stronger than it really is). `entity_convergence_scan.py` now loads each tracked competitor's REAL, already-recorded alias list (`competitor.json`'s `aliases` field — data that already existed and was already being discarded by `_watched_entity_names()`) and passes it through.
